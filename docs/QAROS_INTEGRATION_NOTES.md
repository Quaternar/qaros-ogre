# QarOS integration notes

## App content space

The QarOS header defines the coordinate spaces of its C API in one place, the section on coordinate systems, and every field and function that holds a position, an orientation or a pose names the space it is in. The C API converts no coordinates: each value is exactly what the library produced.

Four of those spaces matter here. **Room space** is the frame that every peer of a session shares; app volume poses and GUI panel poses are given in it, and the XR runtime sets its origin, not the application. **App volume space** is the local frame of one app volume: its origin is the centre of the cuboid, +X runs along the width, +Y up along the height and +Z along the length, in metres. **App content space** is the application's own world inside that box, the space it renders in: app volume space taken into the app pose, with positions divided by the app scale, so in app metres. **View space** is the camera frame of one render view, which looks along -Z.

A render sender that is bound to an app volume hands out the view poses of its views and the hand poses of the device in app content space, and a mapped app volume gesture reports its start point and its action point in app content space, in app units. The header says that an application uses these values as they come.

This stack therefore applies no part of the app volume's placement, that is its pose, its app pose or its app scale, to a view pose, a hand pose or a gesture point. The only change it makes to those values is the change of axes into the ROS world, with the viewer anchor that goes with it. A unit test checks the arithmetic of this: with the transform that the pick path uses, the ROS point of a gesture point is the same for the app scales 1, 0.1 and 10, and a transform that is given the reported placement moves the point. The test builds that transform itself, so it does not run the code that builds it for a live gesture.

The placement is still data that the runtime owns. The default gesture rules map the single-pointer 6DoF gesture to the app pose and the dual-pointer distance gesture to the app scale, so the operator changes both by grabbing and pinching, and the values that were passed when the volume was created go stale. This stack reads the pose, the app pose and the app scale back from the runtime and uses them for diagnosis only.

## Depth encoding

The header says which units the depth values of a frame are related to, but not what they are. A frame carries its depth in views of the type depth. The call that shows a frame takes the near and far distances that the frame was rendered with, in app units, and a `depth_scale`, the factor from the depth buffer's units to the view poses' units. The header does not document the encoding of the depth values, and it does not say what a receiver does with those two fields.

The authors of qar_ogre_adapter observed the following with the QarOS Visualizer and an SDK drop earlier than that of 2026-09-28. It reads the depth texture as the raw window-space depth value in the range 0 to 1, the value that an OpenGL depth buffer holds, and changing `depth_scale` or `rendered_near_far` does not change what it shows. Metric distances in metres therefore display wrongly there: every surface farther than one metre saturates and the scene appears in one flat colour. What other peers do with the depth values is not documented by the SDK.

This stack can write either encoding. The default is the metric linear eye-space distance in metres. With the environment variable `QAR_DEPTH_ENCODING` set to `ndc` it writes the window-space value, `gl_FragCoord.z`, the standard non-linear window depth, and it clears the depth view to 1.0, the value of a depth buffer where nothing was drawn. Set `ndc` for the Visualizer.

The window-space value is reciprocal in distance. A far plane that is wider than the content needs leaves little of the range for the near surfaces, and everything beyond the far plane is clipped away, so choose the far plane for the content. With every frame that it shows, the sender reports the near and far distances it rendered with and the `depth_scale`, 1.0 by default; the Visualizer does not use them.

## World basis

Every 3D space of the C API follows the OpenXR convention: right-handed, +Y up and -Z forward, so a view looks along -Z, and a pose is a position vector and an orientation quaternion stored x, y, z, w.

The ROS world that RViz renders follows REP 103 instead: right-handed, +X forward, +Y left and +Z up.

The camera-local axes of QarOS and of an Ogre camera agree: X right, Y up, looking along -Z. This stack therefore copies a view pose component for component, and it only reorders the quaternion to the w, x, y, z storage of Ogre; the rotation is the same. The world axes do not agree, and a Y-up pose that is fed into a Z-up world tips the viewer on its side.

For Z-up content this stack rotates the QarOS world into the ROS world with ros = (-z, -x, y), which is the unit quaternion (w, x, y, z) = (0.5, 0.5, -0.5, -0.5): QarOS up becomes ROS up and QarOS forward, -Z, becomes ROS forward, +X. The rotation is applied only when the environment variable `QAR_POSE_WORLD` is `zup`; unset, the mapping is the identity. Unit tests check that forward and up map as stated and that the identity orientation becomes the quaternion above.

In `zup` mode the stack then applies a viewer anchor after the change of axes: a yaw about the ROS +Z axis, `QAR_POSE_YAW_DEG`, 180 degrees by default; an eye height along +Z, `QAR_POSE_HEIGHT_M`; and a stand-off behind the facing direction, `QAR_POSE_BACK_M`. The height and the stand-off default to 0, so by default the change affects the orientation only. The code that turns a gesture into a pick reads the same variables, so that a pick uses the same map as the camera.

## Session bootstrap

The SDK is one folder, `bin`, that holds the shared library, the launcher process and every dependency of the two, and it is deployed whole. The header recommends loading the library dynamically: define `QAR_ENABLE_DYNAMIC_LOADING`, put `QAR_IMPLEMENT_DYNAMIC_LOADING` in exactly one translation unit and call `qar_library_load` before any other call of the C API. The program then has no link-time dependency on the SDK, chooses the SDK folder at run time, and lets the dependency libraries of the SDK resolve from the SDK folder instead of from its own.

This stack follows that model. The program's one definition of the function tables is in one translation unit of the component `capi` of qar_ogre_adapter, nothing links an import library, and the one wrapper around the vendored header is `qar_ar_core/qar_streaming_c.hpp`, which defines `QAR_ENABLE_OPENGL` before it includes the header. The vendored loader loads the library by its full path with the flags `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS` and `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`, so Windows searches for the dependencies of the library in the SDK folder first, then in the folder of the host program, the folders that the program added itself and the system folder, and never in the current folder or in `PATH`. That puts the SDK's own runtime files ahead of an older C++ runtime that sits next to a host program such as `rviz2.exe`. It is the order of the search and no guarantee, because Windows uses a module of the same name that the process already holds, whichever folder it came from: see [The QarOS library crashes while it starts](TROUBLESHOOTING.md#the-qaros-library-crashes-while-it-starts).

Two paths must be set. `qar_library_load` takes the library file, `<sdk>/bin/qar-streaming-c.dll`, and the field `runtime_binaries_folder_path` of `QarRuntimeInit` takes the folder that the file came from, `<sdk>/bin`. The runtime starts `qar-runtime-launcher` from that folder; left empty, the runtime still creates sessions but no peer can ever be invited. A relative path resolves against the current working directory. This stack takes the folder from the field `runtime_binaries_folder_path` of the configuration of its session factory, and derives the library file from it unless the field `sdk_library_path` names the file.

The header describes the basic flow, and this stack makes the same calls:

1. `qar_library_init`, once per process.
2. `qar_runtime_create`, with the runtime binaries folder set.
3. `qar_runtime_create_session`, which yields a session invite and not a session.
4. `qar_session_invite_serialize`, then `qar_session_join` with the bytes. This is the only call that produces an active `QarSession`; there is no getter for a current session, so the host keeps the pointer, and `qar_session_destroy` ends the session.
5. `qar_session_invite_peer` with a connection string. The invite is the only source of the id of a target peer, and it returns before the device has joined.
6. `qar_app_volumes_add_volume`, then `qar_render_sender_create` for each peer that streams.

The order differs in two places. This stack reads its own peer id with `qar_session_get_my_spec` before it subscribes to peers, and it creates the app volume before it subscribes to peers and before it invites any, so that the volume already exists when the first peer appears.

QuaternAR states that the session id must be unique and not zero. `qar_session_id_unique` makes such an id, and this stack sets the last byte to 1 should a generated id be all zero.

The runtime starts `qar-runtime-launcher` itself, and QuaternAR states that a host never starts it. The field `launcher_config_json` of `QarSessionCreateInit` is an optional JSON object for the launcher; the SDK does not document its keys. This stack passes `{"enableMixer": true}` unless its configuration asks for something else. QuaternAR suggests `{"enableMixer": false}` as a starting point for debugging, because it removes the mixer and connects the host directly to the Visualizer.

Creating the session needs UDP port 7446: when another program holds it, the call fails with a generic transport error. See [Creating a QarOS session fails because UDP port 7446 is held](TROUBLESHOOTING.md#creating-a-qaros-session-fails-because-udp-port-7446-is-held).

Creating a render sender negotiates a transfer with the receiver, and with an SDK drop earlier than that of 2026-09-28 it had, as far as this stack observed, no bound on its duration. This stack therefore never waits for it on the render thread: it starts `qar_render_sender_create_async`, answers "not yet" to the render tick, and picks up the result on a later tick.

## App volume

An app volume is a cuboid that is placed in the room and that reserves the region a remote 3D application renders into. It is required: `QarRenderSenderInit::app_volume_id` must name a volume that already exists, because the volume is what places the stream in the shared 3D scene, and a stream without one is not positioned in the scene and no viewer can show it. A NULL id is rejected with `QAR_STATUS_APP_VOLUME_INVALID_ID`. Create the volume first with `qar_app_volumes_add_volume` and pass the id that it returns.

The pose of the volume, the field `pose` of `QarAppVolumeInit`, places the centre of the cuboid in room space. The app pose, `app_pose`, is the origin of the rendering application inside app volume space, in volume metres, relative to the cuboid centre; the app scale does not scale it. The app scale, `app_scale`, converts app metres into volume metres: 1.0 renders 1 m of the application as 1 m in the volume, 0.5 makes the application appear smaller and 10.0 bigger. The header states that nothing clips the application to the cuboid: the volume says where the application is meant to be, and gestures and layout are derived from it.

This stack creates one volume when it connects, before any sender exists, and keys every render stream to it. The volume is a cube of 40 m, its centre is raised 1 m along +Y of room space so that the box does not sink below y = 0, its app pose is the identity and its app scale is 1.0. When the volume cannot be created the session stays usable, but no render stream can be created: the sender factory then refuses with a message that says why.

A volume can be pinned to the Earth. The header defines world space as optional and Earth-fixed, ECEF WGS84 in metres in double precision, and a world anchor, `QarGeoAnchorFrame`, as an origin, three unit axes and a handedness in that space. `qar_app_volumes_change_app_world_anchor` sets the anchor of a volume and `qar_app_volumes_clear_app_world_anchor` removes it.

This stack sets the anchor from a geodetic fix. It converts latitude, longitude and the height above the WGS84 ellipsoid, which is the height that the ROS message `NavSatFix` carries and not the height above mean sea level, to the ECEF origin, and it takes the east, north and up directions at that point as the +X, +Y and +Z axes of the anchor, which is the ROS convention. A fix that is NaN or out of range is refused, because NavSatFix reports NaN when the receiver has no lock, and without a volume there is nothing to anchor. Unit tests check that the east, north and up basis is right-handed and that a NaN fix is rejected.

## Peers, invites and admission

A peer enters a session by invitation. `qar_session_invite_peer` takes a connection string, which the SDK builds per device type with `qar_session_invite_connection_string_hololens`, `qar_session_invite_connection_string_quest`, `qar_session_invite_connection_string_visualizer` or `qar_session_invite_connection_string_zed`; only the HoloLens builder takes a parameter, the host name of the device. The launcher reserves an id for the device, starts or attaches it, and returns that id. This is the only source of the id of a target peer: `qar_peer_id_unique` names no peer, and a stream that is created with such an id never produces a frame.

The call returns once the launcher has accepted the invite, which is before the device has joined. Wait for the peer to appear through `qar_peer_subscribe_updates` and to reach the state `QAR_APP_STATE_RUNNING` before you stream to it. Inviting the same host again returns the same id.

`qar_peer_subscribe_updates` reports the peers of a session as they come and go. With an SDK drop earlier than that of 2026-09-28 the authors of qar_ogre_adapter observed that it reported every peer that joined, including the peers that the runtime starts itself: one invited Visualizer appeared as five distinct peer ids. The description of a peer, `QarPeerSpec`, has an id, a display name, an application version, application-defined information, an application state, a version id and a room tag, and no field for the role or the kind of a peer. The display names are generated and, as observed, they change between updates for the same peer id.

This stack therefore streams only to the peers that it admits. The admission policy, `PeerAdmission`, decides which peers these are:

- `kInvitedOnly`, the policy that is in effect unless another one is chosen, admits only the peers that this stack invited itself. It admits every Visualizer that this stack spawned, and it cannot admit a peer that joined on its own.
- `kInvitedOrNew` admits the invited peers and every peer that first appears after a settle window of 5 s that starts when the session is up. It is a timing heuristic for devices that onboard themselves, such as a headset or a Visualizer on another machine, and it exists because the SDK exposes no field for the role of a peer.
- `kInvitedOrNamed` admits the invited peers and the peers whose display name contains a given text. It is not usable, because the display names change.
- `kAny` admits every peer except this process, internal peers of the runtime included. It is meant for diagnosis only.

The own peer is never admitted, and by default at most 8 peers stream at the same time, because every peer costs four renders of the scene per frame, a colour render and a depth render for each of its two eyes; a further peer is refused with a logged warning. A sender that is built for an internal peer of the runtime has the wrong app id, and the runtime then rejects the frames of the Visualizer, because it accepts the frames of a peer only against a sender that was built for its app id.

One Visualizer is one physical head, a pair of eye cameras, so n simultaneous users need n Visualizers, each with its own stereo stream. The connection string that the SDK builds for a Visualizer names no instance, and a repeated invite of the same host returns the same peer, so a second Visualizer cannot be started that way. QuaternAR suggested naming a distinct GUID after the colon of the connection string, because QarOS launches one mixer process per GUID. This stack appends a fresh UUID to the connection string of every Visualizer invite unless its configuration says otherwise, and in the tests of the authors of qar_ogre_adapter two Visualizers streamed at the same time.

## Render-into and the GL context

A render sender can take its frames from an OpenGL context of the host. The sender is created with the graphics API `QAR_GRAPHICS_API_OPENGL` and with exactly one extension on `header.next` that matches the context the host owns: `QarStreamParamsOpenGlEgl`, `QarStreamParamsOpenGlWgl` or `QarStreamParamsOpenGlGlx`. On Windows the header enables only Direct3D 11 by itself, so `QAR_ENABLE_OPENGL` must be defined before the header is included, and this stack defines it in its one wrapper.

This stack requests separated textures and four views in this order: left colour, right colour, left depth and right depth, with the colour format `QAR_PIXEL_FORMAT_R8G8B8A8` and the depth format `QAR_PIXEL_FORMAT_R32_FLOAT`. A frame of the OpenGL sender, `QarVideoFrameOpenGl`, lists its views and its textures with their sizes and OpenGL texture ids. Unlike the Direct3D 11 frame and the Vulkan frame it has no field for synchronisation, and it has no field for the texture target.

The textures that a frame of `qar_render_sender_frame_opengl` carries belong to the library. The header says that the frame is readable before the first begin-frame and writable only inside a frame cycle, so the producer writes into the textures of the library inside the frame cycle. This stack therefore renders with Ogre into its own textures and copies them into the textures of the library, a render-into model. Supplying its own texture ids does not work, because the library overwrites them: the frames then arrive, and the scene is black.

The copy is a framebuffer blit, `glBlitFramebuffer`, on the render thread with the OpenGL context of Ogre current. The textures of the library have the size that the consumer requested, for example 1920 x 1080, while this stack renders each eye at its own size, so the blit rescales. Depth is carried as a 32-bit float colour texture and is blitted with nearest filtering. The library reports one array layer for its textures, but the objects are 2D array textures, and an array texture must be attached one layer at a time for a blit to accept it. After the copy this stack calls `glFinish`, because it has no completion fence to hand back.

The library drives the sender on its own graphics thread, so the host hands it a context for that thread. `QarStreamParamsOpenGlWgl` carries the device context and the OpenGL context, and the context is required: a null context is rejected. The extension also carries `QarOpenGlContextCallbacks`, the functions that resolve OpenGL entry points, make the context current, and capture and restore the binding of the calling thread. They are optional and they are called on the graphics thread of the library, and a function that is left NULL is replaced by the platform implementation of the library. This stack supplies all four.

This stack creates a second WGL context for every sender, shared with the Ogre context so that the library sees the textures of Ogre. It never makes that context current on the render thread, because a WGL context cannot be current on two threads at once and the library binds it on its own thread, which is also why no two senders share a context. The context must be created on the render thread: this stack latches the context that is current there on every tick, and it creates a sender only after a context has been latched.

A frame cycle is `qar_render_sender_try_begin_frame` followed by `qar_render_sender_show_frame`. The call `qar_render_sender_try_begin_frame` starts the begin-frame wait on its first call and polls it without blocking on every later call. This stack uses it from a render tick that must not block, and starts the wait for the next frame right after it has shown a frame, so that the wait runs in the gap between two ticks and each frame costs one tick. This stack treats the status `QAR_STATUS_RENDERING_PRODUCER_STREAM_IS_CLOSED` as the end of the stream of a peer.

The header states that the C API currently supports NVIDIA adapters only; see [The picture is rendered on the wrong graphics adapter](TROUBLESHOOTING.md#the-picture-is-rendered-on-the-wrong-graphics-adapter).

## Gesture rules and the default configuration

The gestures that a peer performs against an app volume are recognised by the peer that renders the volume, and they are mapped through the `QarAppVolumeGestureConfiguration` of the volume before they arrive. What a subscriber receives is therefore already expressed in the frame of the target volume and already filtered by the mapping rules of the volume. The kinds are `QAR_GESTURE_CLICK`, `QAR_GESTURE_HOVER`, `QAR_GESTURE_SINGLE_POINTER_6DOF`, `QAR_GESTURE_DUAL_POINTER_TRANSLATE_DISTANCE` and `QAR_GESTURE_DUAL_POINTER_ROTATE`.

A configuration is a list of mapping rules, `mapping_rules`, and the order of the list is the priority: element 0 has the highest priority. When several gestures are active at the same time for the same volume and the same source peer, the runtime applies only the rule of the highest priority that is active, and it ignores the rules of lower priority until that gesture ends, is cancelled or becomes inactive. A rule names a gesture kind, whether it is enabled, a precision, how the scale of the app changes the sensitivity, the axes of translation and rotation, whether gestures from outside the volume count, the style of the ray (none, solid or dotted, with a colour), and which part of the app transform the gesture drives: none, the app pose or the app scale.

A volume that is created without a configuration, with `gesture_configuration` set to NULL, gets the default configuration of the runtime, which `qar_app_volume_gesture_configuration_default` is written to mirror. It has four rules, in this order of priority:

1. `QAR_GESTURE_DUAL_POINTER_TRANSLATE_DISTANCE`, with precision 2.0, a sensitivity that is based on the app scale, no rotation axes and the mapping to the app scale, so that two hands change the scale of the app; its ray is green.
2. `QAR_GESTURE_SINGLE_POINTER_6DOF`, with precision 1.0, no rotation axes and the mapping to the app pose, so that one hand moves the app; its ray is green.
3. `QAR_GESTURE_HOVER`, with no mapping; its ray is dotted and white.
4. `QAR_GESTURE_CLICK`, with no mapping; its ray is solid and light green.

Pass NULL rather than a configuration that you build by hand: a rule whose ray style is left zeroed has the line style `QAR_APP_VOLUME_CONTROLLER_RAY_LINE_STYLE_NONE`, which is no ray at all. This stack always passes NULL. It reads the configuration back from the runtime for its diagnostic log, and it uses only the click and hover gestures as pointer input, because the manipulation gestures move and scale the volume themselves.

A configuration with a rule that could never work, such as an enabled two-hand rotation that moves the app while it allows no rotation axis, is refused with `QAR_STATUS_APP_VOLUME_GESTURE_CONFIGURATION_INVALID`. The volume keeps its previous configuration, and adding a volume with such a configuration fails the same way.

Whatever the configuration, only one peer at a time moves or scales the app: the first peer whose manipulation binds holds the volume until that manipulation ends, and the manipulations of the other peers are refused meanwhile, while their hover and click gestures still arrive. The extension `QarAppVolumeGestureAllowedPeersExt`, chained from the configuration, restricts the peers whose gestures may move or scale the app. Without it, or with an empty list, every peer may, and a gesture of a peer that is not in the list still reaches the application, unmapped. This stack does not use the extension.

Since the 2026-09-28 drop a volume has gesture modes. A mode is one set of mapping rules that the peers of a volume can be switched between with `qar_app_volumes_select_gesture_mode`. The mode `QAR_APP_VOLUME_GESTURE_MODE_DEFAULT` always exists and cannot be removed, every peer is in it until it is switched, and the configuration of the volume sets its rules. A gesture that is running keeps the mode it began in. This stack defines no other mode, and it does not call `qar_app_volumes_select_gesture_mode`.

## The pointing ray

The pointing ray comes from the gestures of an app volume. The start point of a gesture is the hand: where it was when the gesture began and, for a hover, where it is now; a gesture of two hands starts midway between the hands. The action point is the intersection that the gesture acts on, or the start point when nothing was intersected, so it is absent only when the start point is too, and an absent point is zeroed. The header says that from the start point to the action point is the ray the user is pointing along, which an application can draw itself. Both points are in app content space, the space in which the application renders, in app units.

Equal start and action points therefore mean that nothing was intersected: the aim went into empty space. A hover gesture carries one ray per hand, told apart with `qar_app_volume_gesture_get_hand`, and a gesture of both hands names no hand. The header does not say which geometry the runtime intersects the ray with; that is not documented by the SDK.

This stack subscribes once for the volume with `qar_app_volumes_subscribe_all_gesture_events`, which takes every kind through one reader, and it dispatches on the kind. If that call fails, it falls back to one subscription for clicks and one for hovers. It takes the line from the start point through the action point as its ray whenever the two points are further apart than 0.001 app units, and it treats a closer pair as equal. Unit tests check that the pair is the ray and that equal points are refused as the no-intersection case and not turned into a zero ray.

When the two points are equal, this stack reconstructs the ray as a straight line from the eye through the hand. It does this on the render thread, once per frame, from the newest hand sample of `qar_render_sender_last_hands` and from the view pose of the frame, so that a pick whose target is a plane or a distance along the ray still has a direction. QuaternAR states that QarOS casts a slightly curved ray, so the straight reconstruction agrees with the ray of the runtime closely near the hand and not exactly further away.

A pick whose target is the action point publishes the point that the runtime reported, and only a point that is an intersection with the scene of the app volume, as QuaternAR states it. A click on empty space publishes nothing and is refused with a message, because the action point is then the hand itself; a unit test holds this in place.

The logs of the live sessions of this stack with the 2026-09-28 SDK drop show the hover and click events with the ray of the runtime: in one launch of the RViz plugin the counters of the pointer reached 78,315 hovers and 53 clicks, 1,587 sampled points carried the ray and the point where it met the scene, 21 clicks became published points, and 32 clicks were reported without an intersection and were not published. The authors of qar_ogre_adapter accept a pick when it lands near the aimed object or floor spot, about 0.1 m to 0.2 m at a few metres; they gave no verdict on how near the picks of those sessions landed, and no accuracy figure has been measured.

## Panel pixel coordinates and content_scale

A position on a GUI panel is reported in panel content space, the pixel raster that is drawn onto the panel. The origin is the top-left corner of the displayed image as the viewer sees it, x increases to the right and y increases downward. `QarGuiPanelPoint` holds two signed 32-bit integers, `x_pixels` and `y_pixels`, and both are clamped to the image that the renderer is currently displaying: x is in 0 to content width - 1 and y in 0 to content height - 1.

For a stream panel that image is the video exactly as its sender draws it: the renderer receives the video at the resolution of the sender, and when the renderer has scrolled the video, the position is the pixel under the finger and not a position relative to the visible part. The receiver resolution of a stream panel is taken from the layout of the video sender.

The field `content_scale` of `QarGuiPanelSize` is a zoom of the rendered raster: 1.0 fits the content across the full panel surface, 2.0 shows it at twice the size so that only half of it fits, and 0.5 shows it at half size. It changes how the content is drawn and how a contact maps back to content pixels, and it does not change `width_meters` or `height_meters`. A stream panel ignores it: its video is always drawn at the full panel width and is scrolled vertically when it is taller than the panel.

This stack sends 1.0 as `content_scale` for the panels of the Qt library and by default for URL panels, and never a resolution or pixel ratio, because a value above 1.0 would crop the content and push the position of a contact off its target. The panel of a Qt widget may be rendered at a higher pixel density than its logical size; that ratio stays on this side and is not sent.

The adapter turns a reported pixel into a position on the panel in four steps. It adds 0.5 to x and y, so that the centre of the pixel is addressed, and it divides by the content width and height that the caller of the adapter names. It flips no axis, because the origin of the header, the origin of the panel seam and the origin of Qt are all top-left with y down, and it does not apply `content_scale` again, because the renderer has already mapped the contact through it into content space. A position that lies outside the content, for example after the panel was resized under a live subscription, is clamped to the edge.

The content size is the part of the buffer that the widget covers. This stack aligns the buffer of a panel up to an even number of pixels as a precaution, because video encoders widely reject odd dimensions; the few slack pixels are background, and the position of a contact is normalised against the content size and not against the buffer.

## Panel space

The API of GUI panels is expressed in three frames. Every `QarPose` of this API, the pose of `QarGuiPanelInit`, the pose that `qar_gui_panels_update_pose` sets and the pose that `qar_gui_panel_get_pose` returns, is given in room space, the shared tracking space of the session: right-handed, in metres, +Y up. This stack states the pose of a panel in this frame and passes it unchanged to `QarGuiPanelInit`.

Panel space is the frame that this pose defines. Its origin is the midpoint of the top edge of the panel, the top centre and not a corner, and its axes are right-handed, as a viewer who faces the panel sees them: +X runs along the top edge to the viewer's left, +Y runs up, and -Z is the normal of the front face and points at the viewer. The front normal is -Z and not +Z, because a +Z normal that points at the viewer would not be right-handed. The surface of the panel covers x from -width/2 to +width/2 and y from -height to 0, so a panel hangs below its own pose.

Panel content space is the pixel raster that is drawn onto the surface. Its origin is the top-left corner of the panel as the viewer sees it, +X runs right and +Y runs down, and it is the frame in which `QarGuiPanelPoint` reports positions. It runs backwards along both panel axes: content x = 0 sits at panel-space +width/2 and content y = 0 at panel-space 0, so content x advances along panel-space -X and content y along panel-space -Y.

## Panel input lifecycle

The input of a GUI panel is one stream of gestures: hover, tap, long press and drag. Each gesture carries a phase, one of started, updated, ended, instant and canceled, and a gesture id that ties a started phase to its updates and its end. The peer that draws the panel recognises the gestures from the hand joints of its user, with thresholds that are physical, in millimetres of hand travel against tracking jitter, which a consumer that sees only content pixels cannot reproduce. Every panel reports gestures, URL panels included.

A hover is a lifecycle: started on entry of the fingertip into the hover volume, updated as the content position changes, ended on exit, and it stays open while the same fingertip touches, so that a highlight under the finger survives a press. A tap is instant: the contact was touched and released with little travel and before the long-press duration. A long press is instant and comes once per contact, and the contact may still become a drag afterwards. A drag is a lifecycle: started when the contact crosses the tap threshold, updated for every changed content position, ended on release and canceled when the contact is taken away.

One subscription delivers one kind, and several per-kind subscriptions are separate readers that have no order relative to each other. `qar_gui_panels_subscribe_all_gesture_events` delivers every kind through one reader, so a hover and the drag that grows out of the same contact keep the order in which the producer published them; the header recommends it whenever more than one kind is taken, and says to reconcile on the gesture id, which is shared across kinds within a source peer. This stack subscribes once per panel with the all-kinds subscription.

The gesture that is handed to the callback is an opaque handle to storage that belongs to the library, and it is valid only for the duration of the call: read what you need through the `qar_gui_panel_gesture_get_*` accessors and copy it. The callback runs on a background thread of the library, so it must not block and must not call a subscribe function. This stack reads everything from the handle at the top of the callback and queues samples for the GUI thread.

Several producers publish on the topic of one panel, one per user. The gesture id is unique only within a source peer, so a lifecycle is keyed by the source peer and the gesture id together, as `qar_gui_panel_gesture_get_lifecycle` returns them; the first drags of two users both carry gesture id 1. The source peer is the peer whose hand produced the gesture and not the peer that recognised it. The gesture id is 0 for tap and long press, which are instant. A live lifecycle is republished every 250 ms even when nothing changed, and a lifecycle that is silent for three of those intervals is to be treated as canceled; that, and not the peer list, recovers a producer that crashed. A started phase that was never seen is recoverable, because every update carries its start position. This stack keys on the source peer, the gesture id and the kind, and it cancels a lifecycle after 0.75 s of silence.

A contact that lies outside the letterboxed content rectangle cannot start a lifecycle, but a live lifecycle follows the clamped pixel to the edge and stays there, so a drag that overshoots commits its end value. For the instant kinds the current position and the start position are equal. The timestamp of a gesture is on the clock of the recogniser and is comparable only within one source peer id, so this stack timestamps an event with its own monotonic clock when it arrives. The hand of a gesture is diagnostic, because only one hand of a peer is active at a time; this stack nevertheless treats the two hands of a peer as two pointers, each with its own grab. The tap count is 1, 2, 3 and so on for taps that are close in time and space, and 0 for every other kind.

## Teardown and destroy order

The header documents no order of teardown. It gives these facts about the calls: `qar_library_destroy` frees the process-wide state of the library, and no other call may be used after it until the next `qar_library_init`; `qar_session_destroy` leaves and destroys a session; a subscription whose cancel token is NULL stays alive until the session is destroyed; `qar_gui_panels_close_panel` closes and removes a panel; and `qar_video_sender_handle_destroy` destroys a logical video sender and returns nothing.

This stack closes a GUI panel in three steps, in this order. First it cancels the input subscriptions of the panel, the gesture subscription and the panel-update subscription; the call does not return until no callback for the panel is running, so no callback can name a panel that is being destroyed, and the close that the stack itself makes is not mistaken for a close by the operator in AR. Second it calls `qar_gui_panels_close_panel`, unless the operator already closed the panel in AR, and it reports a failure of the call. Third it destroys the video sender with `qar_video_sender_handle_destroy`, whatever the second step did, because closing the sender first would leave a live panel that refers to a retired stream.

The operator can close a panel in AR. The state of a panel is reported by the subscription of `qar_gui_panels_subscribe_panel_updates`: the state `QAR_GUI_PANEL_STATE_CLOSED` means that the operator closed it, and the runtime republishes a closed panel freely, so this stack reports it once. The states minimised and hidden mean that the operator put the panel away, and the stream continues. When the operator closes a panel in AR, the Qt library stops capturing for the panel and does not touch its adapter or its sender; the teardown comes with the close of the Qt window or the shutdown of the session, and it tells the adapter that the operator already closed the panel.

A subscription is retired in a fixed order too. This stack cancels the token, so that the runtime stops delivering, then gives up the callback slot, so that a callback that is already running finds nothing to touch, and only then destroys the token handle.

QuaternAR states that the current runtime survives the destruction of a stream while other streams run. This stack therefore destroys the sender of a closed panel and forgets the stream.

At shutdown, each render stream first destroys a frame handle that was fetched and not used, and then the stream. The factory destroys the session, then the invite handle, then the runtime, and then, when the library is loaded, calls `qar_library_destroy`. The OpenGL contexts that this stack created for the senders are deleted only after the library is destroyed, so that no context is deleted while a thread of QarOS may still have it current, and the library is unloaded last.

## Hands and view poses

The hand tracking data of a peer comes with a render sender. `qar_render_sender_last_hands` drains everything that arrived from the device since the previous call and returns the last sample. The poses of the hands are in the app content space of the bound app volume, like the view poses. The joint radii and the joint velocities are not converted: they stay in the units and axes of room space, so with an app scale other than 1 a radius does not match the pose of its joint. The pose of a hand, the field `pose` of `QarHandJoints`, is the OpenXR aim pose, and its -Z axis is the hand ray.

Samples arrive only while the target peer is focused on the volume and is not editing it. When nothing has arrived since the previous call, the last sample is returned again while it is younger than a second, so polling faster than the device sends does not blink the hands out between samples. Once no sample has arrived for a second, both hands are reported untracked, because a device that stopped sending has no hands. Poll once per frame; the call returns an error once the hand stream has closed.

The pose of a view comes from the frame information of the render sender. `qar_render_frame_info_get_view_pose` returns the pose to render one view with, in the app content space of the volume: the sender has already taken the room-space pose of the viewer through the pose, the app pose and the app scale of the volume, so the application renders its scene in its own coordinates, and a view of the eye `QAR_VIDEO_FRAME_VIEW_EYE_NONE` gets the head pose. `qar_render_frame_info_get_view_fov` returns the field of view of a view in view space, in radians, and a view without an eye gets the field of view of the left eye.

This stack polls the hands once per ready frame, on the render thread, right after it has read the poses of the two eyes, because that is where both halves of the pointing ray exist at once: the eye pose comes from the frame information of this frame and the hands from the hand sample. The thread of the gesture callback does not poll the hands, because polling from two threads would make each of them read untracked on the calls that the other has drained. A failed call and an empty drain are the same to this stack: an invalid ray.

## Logging control

The library initialisation takes three logging settings: whether the log lines are also written to the console, the folder for the log files, and a severity filter with the levels trace, debug, info, warn, error and fatal. A `QarLibraryInit` that comes from `qar_library_init_default` writes to the console, names no folder and filters at info.

The session factory of this stack asks for trace by default, because QuaternAR asks for full trace-level library logs with every bug report, and it keeps the console copy of the lines on. When the host names no folder, the library writes its files to the folder `quaternar` inside the `TEMP` folder.
A host that runs in normal operation sets `log_severity` of that configuration to `QAR_LOG_SEVERITY_WARN` or a quieter level and `enable_console_logging` to false, as the examples of this repository do, because a trace log is large. It leaves the default, trace, for the log that QuaternAR asks for with a bug report.

The environment variable `QAR_LOG_SEVERITY` takes precedence over the severity field of the initialisation, and a trace log is large. The places of the log files, the precedence rule and the volume of a trace log are described in [Where the QarOS library writes its logs](TROUBLESHOOTING.md#where-the-qaros-library-writes-its-logs), [Which severity applies](TROUBLESHOOTING.md#which-severity-applies) and [How much a trace log writes](TROUBLESHOOTING.md#how-much-a-trace-log-writes).

## The in-AR browser for URL panels

A GUI panel with the extension `QarGuiPanelUrlExt` shows a website: the browser is part of QarOS, and the URL string is copied while the panel is added. The header names no browser engine, no version and no feature set; that is not documented by the SDK. The SDK folder holds the libraries `Ultralight.dll`, `UltralightCore.dll`, `WebCore.dll` and `AppCore.dll`, and the user-agent string in `Ultralight.dll` names Ultralight 1.3.0 on WebKit 610.4.3.1.4, presented as Safari 14.0.3.

The authors of qar_ogre_adapter measured the following with test pages that were opened as URL panels. JavaScript runs, and a WebSocket connection to a ws address works. The CSS property gap on flex containers, the property min-height with the value auto on flex items and the selector :focus-visible are not supported. The viewport of a page is 500 by 500 CSS pixels at a device pixel ratio of 2.0, whatever the size of the panel. Whether text can be typed in AR has not been determined, and whether the viewport can be configured is not documented by the SDK.

## SDK version requirements

A QarOS SDK drop has no version number, so this stack states the drops it supports by their dates: it was verified against the drop of 2026-09-28, and the drop of 2026-09-21 is the earliest SDK drop that provides everything the code calls. [Supported QarOS SDK drops](SDK_COMPATIBILITY.md#supported-qaros-sdk-drops) lists the drops, [Identifying an SDK drop](SDK_COMPATIBILITY.md#identifying-an-sdk-drop) shows how to tell one from another by the hash of its header, and [API changes by SDK drop](SDK_COMPATIBILITY.md#api-changes-by-sdk-drop) lists every change of the header from the minimum drop on.

Four parts of the C API that the minimum drop introduced set the minimum. The code calls each of them, so a drop that lacks one of them lacks something the code needs:

| Part of the C API | What the code does with it |
|---|---|
| `qar_session_id_unique` | `QarCApiSenderFactory` names the session that it creates with the id that this function makes. |
| `qar_gui_panels_subscribe_all_gesture_events` | `QarCApiPanelInputSource` makes this one subscription for every GUI panel that streams a widget. |
| `QarStreamParamsOpenGlWgl` | `QarCApiSenderFactory` chains it onto every render sender, with the four callbacks that tell QarOS how to use the OpenGL context. |
| the field `app_volume_id` of `QarRenderSenderInit`, which must not be NULL | The factory creates its app volume before any sender exists and refuses to create a sender without one. |

The code reads no version at run time, because the SDK has none. What it does check is the library itself. The loader of the vendored header resolves every function that the header declares, refuses the library when one is missing and writes the name of that function to the standard error stream; the session factory then stops and reports that `qar_library_load` failed for the path that it tried. The cause may also be a dependency of the library that Windows cannot find, so a failure of this call alone does not identify the drop: compare the hash of the header as described in [Identifying an SDK drop](SDK_COMPATIBILITY.md#identifying-an-sdk-drop).

## Known SDK limitations

These limits of the SDK are either observations of the authors of qar_ogre_adapter from live sessions, which the SDK documentation does not describe and which have not been repeated on every drop, or places where the header leaves a question open:

- **No call retires a logical video stream.** `qar_video_sender_handle_destroy` returns nothing, and `qar_gui_panels_close_panel` closes the panel and not the stream behind it; the header declares no call that stops, retires or withdraws a stream. The authors of qar_ogre_adapter observed that a receiver that is attached to the stream is not told that the stream is gone: it enters a reconnecting state and retries about every ten seconds, each retry fails with the status 507, and this goes on until its peer goes away. This stack destroys the sender and closes the panel when it retires a panel.
- **A cancelled gesture subscription may leave its runtime subscription.** Cancelling the token stops the delivery of events to the callback, but the header does not promise that a callback that is already running has returned when the cancel call returns, so this stack gives up the callback slot under a lock and never frees the slot. The authors of qar_ogre_adapter also observed that the runtime-side subscription of a panel persisted until the session was destroyed, so a session that opens many panels keeps a pair of subscriptions for each of them.
- **A widget resize needs a new sender.** The receiver of a stream panel takes its resolution from the layout of the video sender, and the SDK does not document whether a change of that layout with `qar_video_sender_change_layout` reaches a receiver that is already attached. This stack therefore creates a new sender when the size of a widget changes.
- **What the runtime intersects a gesture with is not documented by the SDK.** The header names the action point as the intersection that the gesture acts on, and it does not say which geometry is intersected.
- **The viewport of URL panels is fixed.** The page of a URL panel sees a viewport of 500 by 500 CSS pixels at a device pixel ratio of 2.0, whatever the size of the panel, and the SDK does not document a way to configure it.
- **No call asks where the operator is.** The header declares the pose of the viewer, its head and its eyes, only with a render sender: `qar_render_frame_info_get_view_pose` on the frame information of a frame returns it in the app content space of the volume that the sender is bound to, and `qar_render_sender_last_hands` returns the hands of the same sender. A program that streams only panels has no render sender, so it cannot know where the operator stands or looks, and the code of this stack places its panels at fixed positions.
- **A panel that is created again after it was closed can crash the Visualizer.** With a Visualizer attached, the Visualizer crashed in each of the 25 cases, observed by the authors of this stack, in which the plugin qar_rviz_plugin created its hidden Displays panel, a GUI panel, again after it had been closed. The crash came within a second of the creation, every running Visualizer crashed with it, and QarOS started a Visualizer again after several seconds. It happened with the display name unchanged, with a numbered display name, with a shifted position and with a pause of 8 seconds before the start. In one longer session the Visualizer crashed five more times, each within a second of the close or the creation of a panel: twice at the close of the panel of a dialog, once at the close and the creation again of a video panel, and twice at the opening of the page of an AR tool in a URL panel. It did not crash at the other closes and creations of panels in that session. Every crash report names the same access violation at the same place inside `WebCore.dll`, the browser engine library of QarOS. The crash reports are files of the QarOS log folder that are named after the program `qar-stereokit-gui.exe`, which the authors call the Visualizer GUI process. The SDK `bin` folder holds this program next to `qar-streaming-viz.exe`, which this documentation names as the Visualizer elsewhere; how the two programs relate is not documented here. The SDK documents no rule for display names, and the defect is the Visualizer's. The plugin gives every QarOS panel that it starts for a window of RViz or for a video a display name that no earlier panel of its process used: the name that was asked for at the first start, and `<name> (2)`, `<name> (3)` and so on at the later ones. This does not prevent the crash. It does not number the panel that the Qt library of this stack, qar_qt_streaming, creates for a dialog of a streamed window, the panel that this library creates again when the size of a streamed window changes, or the URL panels of the AR tools.
- **Further limits are named where they apply.** The OpenGL frame has no field for synchronisation, the SDK exposes no field for the role of a peer, and the encoding of the depth values is not documented.
